# Laya Tetris

基于 Laya 决策模型的网页版俄罗斯方块：模型替玩家选择落点，**每一步的决策依据**都实时、可解释地展示出来 —— 每个候选落点的中文陈述、`noul` 好落点概率、落点后的量化指标、请求耗时与 token 消耗、最终选中理由，全部可视化。

界面是明亮清爽的休闲游戏风：浅天蓝底 + 糖果色方块、圆角玻璃卡片、3D 黏土质感按钮与柔和阴影；同一套页面在手机上自动变成竖屏游戏布局（顶部分数/等级/连击、中间棋盘、右侧 NEXT/Hold、底部触控方向键），在桌面上则是游戏区 + 决策看板的双栏布局。

## 快速开始

本项目需要一个**本地运行的 Laya 决策服务**（默认 `http://localhost:8000`，协议 `POST /v1/systemone`）。它不随本仓库分发，需要你自行准备；暂时没有也可以先开 **Mock 模式**，全部界面与决策流程都能跑通。

```bash
npm install
npm run dev      # 打开 http://localhost:5173
```

页面顶部的「开始」按钮启动游戏。右上角：

- **Laya 模型**：枚举候选 → 并行询问模型 → 取 `noul` 最高者落子
- **启发式**：纯 Dellacherie 特征评分，不联网（用于对比模型水平）
- **人工**：键盘操作，可随时切回 AI 对比

> 模型还没启动？打开右上角 ⚙ 设置 → 连接 → 打开 **Mock 模式**，就能用模拟概率跑通完整决策流程与看板。

其他命令：

```bash
npm run build     # 类型检查 + 生产构建
npm run preview   # 预览构建产物
npm run verify    # 离线自检：引擎长跑 + 决策管线 + 协议字段校验
```

## 跨域（CORS）解决方案

本地决策服务默认没有开启 CORS，浏览器直连会被同源策略拦截。**推荐方案一，模型端零改动。**

### 方案一：Vite dev server 代理（已内置）

`vite.config.ts` 已把 `/v1` 代理到 `http://localhost:8000`：

```
浏览器  →  http://localhost:5173/v1/systemone   （同源，无跨域）
Vite    →  http://localhost:8000/v1/systemone   （Node 层转发，不受同源策略限制）
```

端口不一致时（例如协议示例里的 `127.0.0.1:18110`），在项目根目录创建 `.env.local`：

```bash
LAYA_TARGET=http://127.0.0.1:18110
```

然后重启 `npm run dev`。设置面板里的端点保持相对路径 `/v1/systemone` 即可。

### 方案二：给模型服务加 CORS 响应头

FastAPI 示例，之后把设置里的端点改成 `http://localhost:8000/v1/systemone` 直连：

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_methods=["*"],
    allow_headers=["*"],
)
```

### 方案三：独立代理 / 关闭浏览器安全策略（仅本地调试）

用 nginx、caddy 或一段 Python 脚本把请求转发到模型服务；或者以 `--disable-web-security` 启动 Chrome。后者会降低浏览器安全性，只建议临时使用。

## 决策协议对接

工程严格按 `noul` 概率评估协议实现，一次请求只评估**一个**候选落点：

```
枚举全部合法落点（旋转去重 × 横向位置 × 硬降模拟）
  → Dellacherie 启发式评分排序，取前 N 个（默认 6，可配 4~8）作为候选
  → 每个候选生成中文陈述 candidate_placement
  → 并行 POST /v1/systemone（Promise.all，并发上限默认 6）
  → 取 answers.is_good_placement.noul 最高的候落子
  → 若最高 noul < 阈值（默认 0.5）或全部失败，降级为启发式最优落点，并在界面标注「启发式兜底」
```

最后一行的降级是可配的：设置 → 决策里的 **「允许启发式兜底」** 关掉后，阈值不再生效，模型无论给出多低的 `noul` 都由它自己决定（直接取最高者），启发式只在**全部请求失败**这种无判定可用的极端情况下才接手。想让模型真正独自打完一局，就把它关掉；想复现协议里的保守降级行为，就保持开启。

请求体（每个候选一次）：

```json
{
  "model": "laya-multilingual-F16",
  "state": {
    "board": "..........\n......##..\n.#####.#..",
    "current_piece": "T",
    "next_pieces": ["I", "L"],
    "candidate_placement": "T 形以「尖朝上」的姿态落在第 4~6 列…",
    "board_metrics": { "lines_cleared": 1, "holes": 0, "max_height": 14, "bumpiness": 2, "well_depths": [] }
  },
  "questions": {
    "is_good_placement": { "type": "noul", "instructions": "这个落点是一个好的落点吗？好的落点应尽量消除行、不制造空洞、保持堆叠低且平整。" }
  }
}
```

响应取值：`answers.is_good_placement.noul`（0~1）、`usage.input_tokens`、`routing.reason`。

设置面板可调：端点、模型名、候选数、并发、超时、是否允许启发式兜底、概率阈值、`instructions`、棋盘行序翻转、Mock 开关、落子动画间隔、重力倍率。全部持久化到 localStorage。

> 协议文档中 `board` 行序存在冲突（字段表写「从最底行写到最顶行」，示例写「第一行是最顶行」）。实现按示例以**第一行 = 最顶行**为准，并在设置里提供「棋盘行序翻转」开关；每张候选卡片都能展开原始请求 JSON 直接核对。

两栏各自是一条完整的纵向信息流：

- **左栏（游戏 + 统计）**：分数条 → 棋盘与侧栏 → 触控 → 运行数据 → 模型决策分析。统计与分析放在一起，因为「校准分布」「时序走势」都是历史数据。
- **右栏（决策流）**：决策流程（本步链条）→ 决策看板（本步候选）→ 决策时间轴（历史逐条）。

看板的候选列表与时间轴都各自限高、内部滚动，不会把右栏无限拉长。

徽章含义：`Laya 判定` 表示模型完成决策；`启发式兜底` 表示模型概率低于阈值或请求失败后按协议降级（关掉「允许启发式兜底」后只剩「请求失败」这一种可能）；`Mock 模拟` 表示离线模拟。

响应式断点：宽屏（≥1024px）为「游戏区 + 决策看板」双栏；窄屏 / 手机为单栏，先游戏后决策，棋盘与侧栏保持同一行、底部控制区固定在内容流末尾。音效是 WebAudio 实时合成的，没有任何音频资源文件，可在底部按钮一键静音。

## 落子演示节奏（可调）

落子过程被拆成四段，全部可在 `设置 → 显示 → 落子演示节奏` 里调节，并提供三个一键预设：

| 阶段 | 含义 | 标准默认 |
| --- | --- | --- |
| ① 落点预览停留 | 决策完成后先高亮目标落点，方块暂不移动，明确“模型选了这里” | 340 ms |
| ② 移动步进间隔 | 每次旋转或平移之间的间隔 | 150 ms |
| ③ 落子前悬停 | 对齐落点后停一下，方便对比幽灵块与目标虚线框 | 300 ms |
| ④ 落定观察窗口 | 硬降后的停留，避免下一条决策盖掉消行闪光 | 280 ms |

预设：**演示节奏**（约 2.6s/块，适合讲解录屏）、**标准**（约 2.1s/块）、**极速**（几乎瞬间，适合压测长跑）。

配合使用：

- **单步**按钮：完整走完一个方块的「枚举 → 筛选 → 询问 → 选优 → 落子」后自动暂停，可一步步观察决策链路。
- **思考期间冻结重力**（默认开启）：模型推理时方块不会自己掉落，避免决策还没回来就触发了锁定。

## 怎么判断「这一步到底是不是模型决定的」

只看最终分数无法区分「模型自己选错了」和「模型根本没参与、全是启发式兜底」。界面为此提供了四类归属，在时间轴的筛选条和「校准分布」里都能看到：

| 归属 | 含义 |
| --- | --- |
| **模型·一致** | 模型独立决策，且恰好选中了启发式最优落点 |
| **模型·分歧** | 模型独立决策，但没选启发式最优落点 —— 模型在主动偏离。时间轴会在这一行标出**比启发式最优低多少 Dellacherie 分** |
| **兜底** | noul 低于阈值或请求失败，按协议降级为启发式最优落点（阈值那一半可关闭，见「决策协议对接」） |
| **启发式模式** | 驾驶模式切到「启发式」跑的步数，与模型水平无关，不计入参与度 |

由它们派生出两个关键数字：

- **模型决策率 / 模型参与率** = 模型独立决策的步数 ÷（模型独立决策 + 兜底）。这个数低，说明阈值卡太死或模型概率整体偏保守，大部分步数其实是启发式在替你玩。
- **平均分歧代价** = 模型偏离时平均每步比启发式最优低多少分。这个数大，说明模型确实在拖后腿。

注意口径：旧版界面的「与启发式一致率」把兜底步也算作一致（兜底时必然等于启发式最优），会虚高一倍以上；现在所有一致性统计都以**模型独立决策的步数**为分母。

排查思路：

- 参与率低 → 调低「概率阈值」，或直接把 **「允许启发式兜底」关掉**（设置 → 决策），让模型在每一步上做决定。关掉后参与率必然接近 100%，此时「模型·分歧」的行数和「均低 N 分」才是模型水平的真实读数。
- 参与率不低但分数远低于「启发式」模式 → 模型在大量偏离，看时间轴里分歧行的「低 N 分」，并逐行展开原始 JSON 核对棋盘行序（`flipBoardRows`）与 `candidate_placement` 陈述是否符合模型预期。
- 分数接近「启发式」模式 → 说明绝大多数步数在兜底，模型实际没怎么参与。

## 实测：这个模型能做什么

如果你跑出来分数不高，先看这一节——**大概率不是你配置错了**。下面是在本机 `localhost:8000` 的 `laya-multilingual-F16` 上测出来的结果，全部对照都做过换序 / 换批，且都先验证过模型是确定性的（同一请求重复发 6 次，`noul` 完全相同，极差 `0.0000`）。

**1. 模型对「候选之间的差异」几乎不敏感。**

| 只改变这一项 | `noul` 的极差 |
| --- | --- |
| 棋盘（`board`） | **0.231** |
| 落点中文陈述（`candidate_placement`） | 0.038 |
| 落点后指标（`board_metrics`） | 0.027 |

同一次决策里 6 个候选共享同一个棋盘，也就是说九成的 `noul` 信号对所有候选是一样的，真正能区分候选的那部分只有 ±0.03。更极端的是：**在 `state` 里新造 `placement_a` / `placement_b` 这类键，模型完全不读**——14/14 组两个候选拿到逐位相同的 `noul`，极差 `0.0000`。模型只认它已知的槽位（`candidate_placement`）。

**2. `noul` 与落点质量系统性反相关。**

同一个盘面、同一个方块，沿 Dellacherie 排名等距取 5 个落点打分：28 组「盘面 × 方块」里，组内 Spearman 相关系数集中在 **−0.48 ~ −0.90**。也就是说落点越差，模型给的分越高。这不是没区分度，方向是反的。

配合「启发式最优 vs 最差」的大差距对照（Dellacherie 分差 56~268 分）：

| 场景 | 随机水平 | 实测 |
| --- | --- | --- |
| 真实决策：在启发式前 6 名里选 | 17% | **25%**（5/20） |
| 大差距对照：最优 vs 最差选一个 | 50% | **48%**（23/48） |

**3. `noul` 随盘面越危险越高。**

| 盘面 | `noul` 均值 |
| --- | --- |
| 空盘 | 0.72 |
| 堆高 4 层 | 0.87 |
| 堆高 8 层 | **0.98** |
| 堆高 12 层 | 0.96 |

配上固定阈值 `0.5`，意味着**开局空盘时大量触发兜底、残局濒死时几乎不触发**——和「越危险越需要帮忙」正好相反。这是「概率阈值」这个参数在本地模型上失效的原因。

**4. 成对比较（一个请求给两个候选）三种形态全部无效。**

| 形态 | 换序一致率 | 结果 |
| --- | --- | --- |
| `choice` 题（`criteria` 用 label → description） | 7% (1/14) | 几乎恒定判「第一个更差」，位置偏置压倒内容 |
| `noul` + `true`/`false` criteria | 29% (4/14) | 通道探测只有 1/14 真的在读 criteria 文本 |
| 同一请求里两个独立的绝对 `noul` | — | 两个候选拿到逐位相同的分数（见第 1 条） |

**5. 批量请求不省时间。** 一个 HTTP 请求里塞 N 个问题，耗时近似线性：1 题 425ms → 12 题 4472ms（12 倍题数放大 10.5 倍），每题约 360ms，固定开销只有约 130ms。好处是批次之间**零串扰**（同一份内容在 1/2/4/6/12 题的批次里读数完全一致）。所以成本就是 `请求数 × 0.36s`，跟怎么打包无关。

**6. 语言：英文确实更好，但只在「差距大」的时候。** 英文 `state` + 英文 `instructions` 会把上面第 2 条的相关系数从负翻正（三次独立测量：+0.37 / +0.365 / +0.236，中文侧是 −0.57 / +0.046 / −0.232），大差距对照正确率 **71%（34/48）vs 中文 48%（23/48），p = 0.003**。但换到真实决策（前 6 名之间选），优势缩到 40% vs 25%，**p = 0.25，不显著**。英文能分清「好」和「烂」，分不清「好」和「还行」——而游戏里只需要它做后者。

**结论**：分数低主要不是工程编排的问题。工程侧已经逐项排除过：棋盘行序（正序/翻转都测了）、超时与重试（本地服务是串行推理，见下节）、落点枚举重复（`I`/`S`/`Z` 的 180° 对称已去重）、argmax 取值。模型的 `noul` 对「同一个盘面下哪个落点更好」这个判断本身携带的信息极弱，且方向偏反。

顺带记两条协议细节（服务端 422 报错正文本身就是文档）：

- `choice` 题的 `criteria` 是 **label → description 的字典**，或者 label 数组：`{"A": "描述A", "B": "描述B"}`。响应里读 `answers.<name>.probabilities.<label>`。
- `noul` 题的 `criteria` 只能以 `true` / `false` 为键，这两个键就是模型读到的选项文本；想换措辞用 `labels`。省略会被静默替换成默认文本。

## 调参建议

- **延迟太高**：本地服务是串行推理（见下节），**调并发没用**——真正能降耗时的只有把候选数降到 4，或缩小 `board_metrics` 的上下文。协议文档里「单次推理约 30~170ms」是按单发估的，实际排队后要乘候选数。
- **模型决策不稳**：关闭「允许启发式兜底」让模型完全接管，或把「概率阈值」降到 0.3 保留部分保护；也可修改 `instructions` 明确评判准则。
- **想看清楚决策过程**：用「演示节奏」预设 + 「单步」按钮；棋盘上的虚线框是模型选中的目标落点，其余浅色残影是落选候选。
- **想看模型是否真的比启发式强**：切到「启发式」模式跑一段，对比分数与「校准分布」里的模型参与度三分类（见下节）。
- **压测**：用「极速」预设 + 重力倍率拉到 20×，观察 PPS 与「时序走势」里的耗时曲线。

## 排查：「模型接口明明能通，游戏里却全是启发式兜底」

这是最容易踩的坑，症状是时间轴整屏 `启发式兜底`、分数跟纯启发式模式差不多，但用 Postman / curl 单独打同一个端点却秒回 200。

**原因：本地 Laya 服务是串行推理的。** 实测单个请求约 0.32s，同时发 6 个不会并行，而是一个个排队：第 1 个 0.37s、第 2 个 0.69s、第 3 个 1.00s……第 6 个 1.92s。所以**并发数不改变总耗时**，`候选数 × 0.35s` 才是单步决策的物理下限。

于是「单次超时」必须按这个下限来估，不能按单个请求估。默认值调到 **6000ms** 就是为此；如果你的服务更慢，继续往上调（设置 → 决策，上限 20000ms）。

配套的两个改动：

- **超时不再重试**。服务在排队时立刻重发，只会把新请求塞回队尾、把队列拉得更长，让后面的候选跟着一起超时——实测会连锁到 6 个候选全灭。现在只对网络抖动类失败重试。
- **「测试连接」按真实候选数并发打一轮**，而不只是探测端口活着。单发一个请求永远会通过，看不出超时问题；现在它会报「6 个候选全部返回，最慢 2.11s（超时 6000ms）」，超时不够就会直接点名有几个候选失败。

排查顺序：设置 → 连接 → **测试连接** → 若报「N 个候选有 M 个失败」，把「单次超时」调高再测，直到全部返回。
